# Platform modules and Terraform delivery

These additions are on `feature/all-public-modules`. Existing networking code is
unchanged. No cloud resources or GitHub settings have been changed.

## Layout

Each reusable module has `main.tf`, `variables.tf`, `outputs.tf`, and `versions.tf`.
Deployment roots own provider configuration, API enablement and separate GCS state.

| Root under workloads/prod | Module | Purpose |
|---|---|---|
| cache | redis | Private Memorystore Redis, HA by default, AUTH, TLS and deletion protection |
| registry | artifact-registry | Docker repositories, immutable tags and additive repository-scoped IAM |
| secrets | secret-manager | Protected secret containers, automatic/regional replication and per-secret access |
| identity | workload-identity | Google service accounts, GKE impersonation bindings and optional project roles |
| argocd | argocd | Pinned Argo CD Helm release and namespace, internal service, TLS, atomic upgrades |

Do not run these modules directly. Terraform run from `workloads/prod` does not
load its subdirectories; each new root must be initialized and deployed separately.
There is no state migration from networking into these roots.

## Prerequisites and deployment order

1. Existing GCP project, billing, approved credentials and a protected/versioned
   GCS state bucket. Each `backend.hcl.example` has a distinct state prefix.
2. Existing network. Cache defaults to PRIVATE_SERVICE_ACCESS and requires the
   network owner to establish PSA first; the current networking branch does not
   wire its PSA input. DIRECT_PEERING is explicit opt-in. Review CIDRs/quotas and
   maintenance timing with the network owner. Capacity examples are not sizing approval.
3. Deploy identity, registry and secrets. Grant the **GKE node service account**
   repository-reader access for image pulls; Workload Identity alone does not
   give the kubelet access. Build identities get repository-writer access.
4. Existing GKE cluster with Workload Identity enabled on the cluster and the
   relevant node pools. This branch's GKE files are still placeholders. Apply the
   returned `iam.gke.io/gcp-service-account` annotation to each existing Kubernetes
   service account in application manifests. Namespace and KSA names must match
   the bindings exactly. This module creates Google accounts, not Kubernetes objects.
5. Argo CD needs a runner with connectivity to the existing GKE API, Google ADC,
   `gke-gcloud-auth-plugin` and sufficient Kubernetes permissions to install CRDs,
   cluster roles and chart resources. It uses the existing cluster's advertised
   endpoint and CA. Keep its endpoint reachable by that runner; for private-only
   clusters use the trusted `gke-private` self-hosted runner label. Enable the GKE
   API before this root's cluster data lookup.
6. Have an administrator configure GitHub-to-GCP federation, plan/apply service
   accounts and their IAM permissions, then configure GitHub environments. The
   pipeline uses these preconfigured identities; it does not provision them.

For each root, copy `terraform.tfvars.example` to `terraform.tfvars` and
`backend.hcl.example` to `backend.hcl`. Replace all placeholder IDs, names,
identities and numeric repository/owner IDs. Region defaults to asia-south1.
Examples are not automatically loaded by Terraform.

```powershell
terraform -chdir=workloads/prod/registry init -backend-config=backend.hcl
terraform -chdir=workloads/prod/registry plan -out=deployment.tfplan
# Review the saved plan before running an apply.
terraform -chdir=workloads/prod/registry apply deployment.tfplan
```

API resources keep APIs enabled on destroy. Account grants are additive IAM
members and do not replace unrelated IAM policy. Review destructive changes to
repository contents and identities. Redis and secrets have deletion protection;
intentional deletion requires changing that setting in code first.

## Secrets and Argo CD boundaries

Secret Manager accepts no secret payloads. Populate secret versions through your
approved external process. Grant runtime identities access only to named secrets.
GKE Secret Manager integration/CSI mounting, application secret references and
secret rotation are application/cluster configuration; they are not provisioned here.

Redis AUTH is generated by GCP. Terraform provider state can still contain that
credential even though this module does not export it. Protect state and saved
plans, retrieve AUTH through an authorized runtime process, and configure client
TLS using the returned server CA certificates.

Argo CD is an internal bootstrap using pinned chart 10.18.0. Configure reviewed
SSO, RBAC, HA sizing and application repositories through its YAML values and
GitOps manifests. The chart's initial admin secret stays in Kubernetes; do not
copy it into tfvars. No public ingress, Git repository credentials or Argo CD
Applications are invented. Use an authenticated port-forward to bootstrap access.
Do not include credentials in Helm values; Helm provider state stores values.
Argo CD's bundled Redis is separate from the application Memorystore cache.

## Terraform CI/CD

`terraform-checks.yml` runs format checks, initialization without a backend,
validation, module tests and deployment-root mock plans for all five roots on PRs
and selected pushes, and can also be started manually from GitHub Actions. The helper also checks the actual planned resource graphs
for input forwarding, security settings and resource-scoped IAM.
It has no Google credentials and does not run untrusted PR code on private runners.
Existing networking is outside this workflow's validation scope because its review
findings are being handed back to its owner.

`terraform-deploy.yml` is a manual workflow restricted to main. Choose a layer
and `plan` or `apply`. A credential-free checks job must succeed before planning.
Plan uses an environment-specific OIDC identity, locks the
backend and saves a binary plan. The apply job checks out the same commit,
downloads that exact plan and lock file, verifies the manifest matches the layer,
commit, expected GCP project, backend, lock file and plan bytes, rejects plans older than 24 hours, and
applies the saved plan without replanning. Workflow concurrency serializes
runs per layer. Binary plan artifacts expire after one day and may contain
sensitive infrastructure data; restrict repository Actions access accordingly.
Artifact names include the workflow attempt number; apply downloads the exact
artifact ID emitted by its plan job, including when only failed jobs are rerun.
Before upload, the parsed Terraform plan must target the environment's
`GCP_PROJECT_ID` in both its root input and explicit Google resource project
fields (including resources being deleted). Apply must use the same project.
The temporary plan JSON may contain sensitive values and is cleaned locally,
not uploaded. All action references are pinned to commit SHAs.

For EACH layer, create these GitHub environments:

- `tf-plan-LAYER`: read-oriented project identity plus state-lock permissions.
- `tf-apply-LAYER`: separate apply identity. **Configure required reviewers,
  prevent self-review and restrict deployment branches to main.** YAML references
  the environment, but GitHub environment protection must be configured in the UI
  or organization automation; this repository has not changed those settings.

In both environments set variables `WIF_PROVIDER`, `TF_SERVICE_ACCOUNT`, and
`GCP_PROJECT_ID` using administrator-provided identity details. Set secret `BACKEND_HCL` to the
same bucket/prefix configuration in both environments. Set plan-environment
secret `TFVARS_HCL` to the reviewed layer inputs. Backend HCL must contain only
bucket/prefix settings, with authentication supplied through OIDC/ADC.

Ask your administrator to restrict federation to immutable numeric repository and
owner IDs, `refs/heads/main`, and the exact deployment workflow path. Bind each
service account to its intended GitHub environment. Use keyless OIDC authentication
and protect main and workflow code through branch reviews.

Configure separate plan/apply identities for each layer you intend to deploy:

| Layer | Typical apply permissions to review |
|---|---|
| cache | roles/redis.admin |
| registry | roles/artifactregistry.admin |
| secrets | roles/secretmanager.admin |
| identity | roles/iam.serviceAccountAdmin; project IAM management only if project_roles is used |
| argocd | cluster read + approved Kubernetes cluster administration for Helm |

All roots enable APIs, so apply identities also need the relevant service usage
administration permissions. A starting plan role set is viewer, IAM security
reviewer and service usage consumer; verify actual read permissions per resource.
Do not grant production IAM administration just to make a plan succeed.
The administrator must grant backend access for state reads, updates and locks,
including plan locks. Keep that access scoped to the intended state bucket/trust
boundary. This repository does not provision CI identities or state buckets.

## Local state in this checkout

Each new root currently has an ignored `backend_override.tf` selecting the local
backend with `terraform.tfstate` in that root. Local init needs no GCS bucket or
backend credentials:

```powershell
terraform -chdir=workloads/prod/registry init
```

The override is local to this checkout; the checked-in GCS configuration remains
for CI/CD. Do not pass `backend.hcl` while the local override is active. Before
switching a root with existing local state to GCS, review ownership and migrate
that state deliberately; do not initialize an unrelated empty state over it.
A real plan still requires project inputs, Google credentials and any referenced
existing resources.

## Local checks

Terraform 1.16.6 is pinned in Actions. Python 3 and provider downloads are required:

```powershell
python -m unittest discover -s tools/tests -v
python tools/check_terraform.py
# Or: python tools/check_terraform.py --layer registry
```

Checks initialize with read-only provider locks and use mock providers without
contacting GCP/Kubernetes or the GCS backend. They verify module contracts, root
input forwarding, planned resources, security settings, IAM members, replication,
GKE identity subjects and Argo CD settings. Invalid project IDs, Redis capacity
and maintenance hours, malformed Helm YAML and empty inventories are tested.
Command timeouts fail the checks rather than hanging indefinitely.
They do not prove live permissions,
cluster connectivity, Helm chart installability, state ownership or cloud quotas.
Provider versions are pinned per root and provider lock files are committed.
Refresh them deliberately using `terraform providers lock` when upgrading.


See `VALIDATION.md` for the latest offline verification results. No GCP project,
cluster or federation identity is assumed to exist. Creating those prerequisites
and proving real cloud permissions are separate from the offline checks here.
